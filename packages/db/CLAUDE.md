# @repo/db

Kysely + Postgres. **Source-only** — exports `./src/index.ts` and
`./test-support` directly (no build step; picked up live in dev).

## Layout

- `src/client.ts` — validates `POSTGRES_*` via `@repo/env` `parse()`, builds a
  `pg.Pool` (max 10), exports `db` (`Kysely<DB>`) and `pool`. Sets a pg type
  parser for OID 1082 (`date`) so dates stay raw `YYYY-MM-DD` strings.
- `src/migrator.ts` — `createMigrator(db)` factory (Kysely `Migrator` +
  `FileMigrationProvider` over `src/migrations`). Shared by the CLI and tests.
- `src/migrate.ts` — `migrateToLatest()` CLI over `createMigrator`. Run via
  `pnpm migrate`.
- `src/migrations/*` — `YYYYMMDDTHHMMSS-kebab-desc.ts`, each exports `up`/`down`.
- `src/migration-helpers.ts` — reusable ADR-0011 migration utilities
  (`withStandardColumns`, `makeAppendOnly`, `attachUpdatedAtTrigger`, …).
  Exported as the `@repo/db/migration-helpers` subpath; **not** re-exported from
  the package root (migration-only code). Lives outside `src/migrations/` because
  `FileMigrationProvider` treats every file there as a migration.
- `src/ids.ts` — `newUuidV7()` app-side UUIDv7 helper (re-exported from root).
- `src/types.ts` — **GENERATED by kysely-codegen. Never edit by hand.** Re-run
  `pnpm migrate:generate` after schema changes. Prettier-ignored.
- `src/index.ts` — re-exports `db`/`pool`, `newUuidV7`, `DB` + table types, and
  `XxxRecord = Selectable<Table>` / `NewXxx` / `XxxUpdate` aliases.
- `src/test-support.ts` — faker factories + schema-aware `truncateAll` for tests.
- `.kysely-codegenrc.json` — maps `CHECK (col IN (...))` columns to literal
  unions (e.g. `user.role → Generated<'admin' | 'agent'>`). Inline literals only
  — never import from `@repo/trpc` (circular).

## Foundations conventions (core plan 01 — ADRs 0008/0011/0012/0004)

Every table added by plans 02+ is built against these. They are mechanical, not
tribal knowledge — match them.

### Schema-qualified tables (ADR-0008 — DECIDED)

Fully qualified names **everywhere**; no `search_path` manipulation.

- Modules own a Postgres schema: `platform` (shared services) and `hr` (HR
  module). Better Auth tables and Kysely's bookkeeping stay in `public`.
- Migrations: `db.schema.createTable('platform.person')`,
  `createSchema('platform').ifNotExists()`; raw `sql` fragments are written
  schema-qualified.
- Queries: `db.selectFrom('platform.person')` — the dotted key **is** the
  type-safe table name (kysely-codegen keys non-`public` tables as
  `'<schema>.<table>'`). `db.withSchema(...)` is **banned** (it reintroduces
  implicit resolution).
- **Boundary rule (review-blocking):** a module never reads another module's
  tables. A string-literal `'platform.'`/`'hr.'` table key used outside its own
  module's directory is a review-blocking violation (ESLint cannot see table
  strings — grep + review catch it). Cross-module access goes through the other
  module's exported service surface; cross-module notification goes through
  domain events (plan 02).

### Standard columns & soft delete (ADR-0011)

`withStandardColumns(builder, opts?)` (from `@repo/db/migration-helpers`) adds
`created_at`/`updated_at` (`timestamptz NOT NULL DEFAULT now()`), `deleted_at`
(soft delete), and `created_by`/`updated_by` (`uuid`, NULL = system actor, no FK
by default). Options: `{ softDelete?, actorStamps?, updatedAt? }` (all default
true). Pair with `attachUpdatedAtTrigger(db, 'platform.<table>')` so `updated_at`
is trigger-maintained, never set per-procedure. **Soft delete only** — set
`deleted_at`; every read path excludes `deleted_at IS NOT NULL`. Hard deletes are
reserved for the plan 16 erasure process.

### Append-only tables (ADR-0011)

`makeAppendOnly(db, 'platform.<table>')` makes immutability a **database
property**: it REVOKEs UPDATE/DELETE/TRUNCATE from PUBLIC **and** attaches two
triggers running `platform.append_only_guard()` — a row-level
`BEFORE UPDATE OR DELETE` trigger and a statement-level `BEFORE TRUNCATE` trigger.
Both are needed because the Phase 1 dev role is a superuser that bypasses REVOKE;
triggers fire regardless of role, so even the owner cannot rewrite history. The
single exception is the future `cdf_erasure` role (plan 16 / ADR-0019); until it
exists, no session passes the guard. Use for journal, ledger, transition-log and
signature-evidence tables. Append-only tables carry `created_at` only — no
`updated_at`/`deleted_at` (`withStandardColumns(b, { updatedAt: false,
softDelete: false })`). `dropAppendOnly` reverses it (for `down` migrations).
`truncateAll` (test-support) skips append-only tables automatically.

### App-side UUIDv7 keys (ADR-0011)

Primary keys are `uuid` columns with **no** DB default; generate them app-side
with `newUuidV7()` (from `@repo/db`) when constructing rows, so a correlated
write in one transaction can reference the id before insert and a missing id
fails loudly. `@repo/domain` never generates ids — they are passed in.

### History-mechanism classification (ADR-0012)

Before designing any table, classify it and record the mechanism in the owning
plan's §4:

| Data class                   | Mechanism                                    |
| ---------------------------- | -------------------------------------------- |
| Business facts / activity    | Event journal (append-only, plan 02)         |
| Quantitative balances        | Ledger (append-only)                         |
| Key mutable fields           | Field-history table                          |
| Temporally versioned ref/cfg | Effective dating (`valid_from`/`valid_to`)   |
| Rules consumed by long cases | Snapshot-on-use (jsonb on the consuming row) |
| Process state                | Transition log (plan 07)                     |
| Everything else              | `updated_at` + journal events for changes    |

If journal/ledger/transition/evidence → apply `makeAppendOnly`. Nothing relies
on "we'll add audit later".

### Literal-union codegen overrides (ADR-0004)

Whenever a migration adds/changes a `CHECK (col IN (...))` column (or one
matching a Zod enum): add/update the entry in `.kysely-codegenrc.json`
`overrides.columns`, keyed schema-qualified for module tables (e.g.
`"platform.scheduled_action.status": "'pending' | 'claimed' | 'done'"`) —
**inline the literals, never import from `@repo/trpc`** — then regenerate with
`pnpm --filter @repo/db migrate:generate`. Workflow states and event kinds are
always such columns.

## Conventions

- Data records carry `created_at`/`updated_at` (and `deleted_at` on app tables).
- Use `Selectable`/`Insertable`/`Updateable`, never inline record types.
- Auth tables are snake_case; the app-side Better Auth config maps its camelCase
  fields onto them.
- Migration/seed scripts log via `console` (standalone CLIs that must run without
  the built `@repo/logging` artifact).
